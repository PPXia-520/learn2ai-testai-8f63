# 前端异步与网络请求调研报告

## 一、是什么：单线程下的「非阻塞」设计

异步与网络请求是前端开发从「写静态页面」迈向「写应用」的分水岭。它的核心思想其实源于一个硬约束：JavaScript 是单线程的，主线程只有一条执行栈。如果某段代码像传统同步程序那样，发起一个网络请求后傻等服务器返回，那么在这段等待时间内，整个页面都无法响应用户的点击、输入和滚动，界面会直接卡死。

所谓「异步」，本质就是**先注册好回调，等结果到了再执行**，而不是原地等待。浏览器内部靠「事件循环」来协调这一切：同步代码先一口气执行完，随后不断地从任务队列里取出已经就绪的回调逐个执行。一个经典例子是 `setTimeout(() => {}, 0)` 的回调不会立即执行，而要等当前同步代码全部跑完，因此输出顺序总是 1、2、3 而不是 1、3、2。这个机制让耗时操作（网络请求、定时器、文件读取）不再阻塞主线程，页面始终能保持流畅交互。

理解异步，重点是理解「结果不是现在就有」。回调函数是最早的表达方式，但层层嵌套会形成难以维护的「回调地狱」；Promise 则把「未来才有的值」抽象成一个对象，它只有三种状态——进行中（pending）、成功（fulfilled）、失败（rejected），一旦从进行中转为成功或失败，状态就固定不变。这为后续的链式调用、统一错误处理提供了统一的模型。

## 二、怎么用：从 Promise 到 async/await

现代前端最常用的写法是 `async/await`，它本质上是 Promise 的语法糖，让异步代码读起来像同步代码。一个典型的最小示例是：

```javascript
async function loadDashboard(userId) {
  try {
    const user = await fetchUser(userId);       // 拿到用户
    const orders = await fetchOrders(user.id);  // 再拿订单
    return { user, orders };
  } catch (err) {
    console.error('加载失败', err);
  } finally {
    hideLoading();
  }
}
```

这里有几个关键点需要牢记：第一，`async` 函数无论如何都会返回一个 Promise，即使你写 `return 42`，调用方拿到的也是一个包裹了 42 的 Promise；第二，`await` 只能出现在 `async` 函数内部（或模块顶层），并且会「暂停」当前函数直到右边的 Promise 敲定；第三，错误处理靠 `try/catch` 捕获，忘记捕获会导致未处理的 Promise 拒绝。

当多个请求之间没有依赖时，应当用 `Promise.all` 让它们并发执行，总耗时取决于最慢的那个，而不是逐个相加。若需要「无论成败都拿到全部结果」，则改用 `Promise.allSettled`；给请求加超时则常用 `Promise.race` 配合定时器，或直接用 `AbortController` 主动取消。

调用接口则依赖 `fetch`。一个容易踩坑的地方是：`fetch` 只在网络故障时才 reject，服务器返回的 4xx、5xx 状态码依然会 resolve，因此必须手动检查 `res.ok`，再调用 `res.json()` 解析响应体。

## 三、用在哪：一个商品列表页的落地

异步与网络请求几乎贯穿每个真实产品。以一个电商「商品列表页」为例：页面加载时，前端会向 `/api/products` 发起 GET 请求拉取商品数据，同时并行请求 `/api/categories` 获取分类，用 `Promise.all` 合并两次结果后一次性渲染，避免界面「先空着一半」。

用户点击「加入购物车」时，页面会 POST 到 `/api/cart`，并同时做两件事：一是给按钮加防抖、禁用，防止快速连点导致重复下单；二是用 `AbortController` 挂上超时，网络异常时及时取消并给出友好提示，而不是让用户无限等待。用户切换页面或离开组件时，未完成的请求也要被取消，否则可能出现「组件已卸载却还在 setState」的内存泄漏警告。

在表单上传图片的场景里，`fetch` 配合 `FormData` 是标准做法，而且不要手动设置 `Content-Type`，交给浏览器自动带上 multipart 边界即可。可以说，掌握了异步与网络请求，才算真正理解了前端应用如何与后端协作、如何在慢网络下依然保持可用。
